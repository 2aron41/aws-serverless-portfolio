## Partial Apply Recovery

The existing serverless inquiry production history already contained a real
partial-apply recovery.

That incident reinforced:

- inspect live resources first
- inspect Terraform state
- identify exactly what completed
- fix the desired-state cause
- inspect tainted resources before changing taint
- generate a fresh recovery plan
- prevent unexpected replacement or destruction
- apply only reviewed remaining work
- verify final convergence

The Day 44 runbook now explicitly prohibits blindly rerunning a failed apply.

## Recovery Stop Conditions

Stop recovery on:

- wrong or unverifiable AWS account/environment
- unknown failure domain
- unrelated repository changes
- unexpected Terraform state
- unexplained plan additions
- unexpected replacement
- unexpected destruction
- saved-plan mismatch
- proposed weakening of production safety controls

Never:

- use `terraform destroy` as rollback
- make the production S3 bucket public as a shortcut
- manually hide or clear a real alarm
- blindly rerun a failed apply

## What I Learned

Recovery is not the same as undoing the most recent command.

The recovery method depends on the failure domain.

Application code, Terraform configuration, partial applies, Terraform state,
API Gateway configuration, and operational alarms each require different
recovery behavior.

I also learned that a rollback capability must actually exist before a runbook
can depend on it. Because the current Lambda uses `$LATEST` without published
versions or aliases, the supported recovery path is currently Git and
Terraform based rather than an instant Lambda alias rollback.

The safest recovery procedure starts with diagnosis and stops whenever the
planned action cannot be explained precisely.
